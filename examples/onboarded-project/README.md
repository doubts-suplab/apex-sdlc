# Onboarded Project — worked example of the eeik front door

This directory is **generated by the APEX onboarding front door** from an eeik example manifest
(`greenfield-java-aws` — a Java 21 / Spring Boot / AWS microservices platform). It shows what onboarding
produces before the SDLC runs: the project's `CLAUDE.md`, a normalized manifest, and a scaffold plan with
resolved capability packs.

Everything here is produced **deterministically and offline** — no LLM, no network, no credentials.

## Regenerate

```bash
cd platform/backend
LLM_PROVIDER=stub python -m app.demo.onboard_project            # greenfield-java-aws (default)
LLM_PROVIDER=stub python -m app.demo.onboard_project poc-ai-agent   # or another eeik example
```

## What's here

| File | What it is |
|---|---|
| `CLAUDE.md` | The onboarded project's context file (identity, stack, active capability packs, governance) |
| `project-manifest.yaml` | The normalized, validated eeik manifest |
| `scaffold-plan.md` | Repository layout + resolved packs (built/stub/planned) + recommended eeik agents + APEX hand-off |
| `registration.json` | The record APEX registers — the project enters at the **Requirements** phase (the spec-driven spine) |

## How it works

The bridge is a deterministic transform over eeik's structured data (vendored under
`platform/backend/app/onboarding/eeik_assets/`, see its `PROVENANCE.md`): the manifest is validated, the
`capability-matrix.yaml` resolves it to capability packs, and a scaffold is generated. The project is then
registered at the Requirements phase, handing off to the seven-phase governed journey.

> **Boundary:** this produces the onboarding *context + scaffold plan*, not a full compilable repo tree
> (that is the LLM-driven eeik `repository-generator`, a follow-on). See
> [`docs/progress.md`](../../docs/progress.md) and [ROADMAP Phase 0](../../ROADMAP.md#phase-0--onboarding-the-eeik-front-door).
